# Project Index

## What This Project Does

`samhorse` is an Astro 6.x static website — a portfolio for an equestrian career (horses, tournament results, photo gallery). It uses Astro's file-based routing, TypeScript strict mode, the Content Layer API for data-driven pages, and Tailwind v4 for styling. The full site is built: home, horses listing + per-horse detail pages, tournaments, and a filterable photo gallery.

## Project Structure

| Path | Purpose |
|------|---------|
| `src/pages/` | Routes: `index.astro` (home), `horses/index.astro`, `horses/[id].astro` (per-horse detail), `tournaments.astro`, `gallery.astro` |
| `src/layouts/BaseLayout.astro` | HTML shell: head/meta, skip-link, `Header`, `Footer`, `<slot/>`. Takes `title`/`description` props |
| `src/components/` | `Header` (responsive nav), `Footer`, `HorseCard`, `TournamentList`, `PhotoGrid` |
| `src/site.ts` | Site metadata (`SITE`), nav list (`NAV`), and the `horseAge(foaled)` helper |
| `src/types.ts` | Shared view-model types (`TournamentItem`, `PhotoItem`) passed into components |
| `src/styles/global.css` | Tailwind import + `@theme` design tokens (colors, font) + base styles & focus ring |
| `src/content.config.ts` | Content collection definitions (`horses`, `tournaments`, `photos`) with Zod schemas |
| `src/content/` | Collection data: `horses/*.md` (bio in body), `tournaments/*.yaml`, `photos/*.yaml` |
| `src/assets/` | Local images referenced by collections via the `image()` schema helper, so Astro optimizes them. Never put browser-facing images in `public/`. |
| `public/` | Static assets served verbatim at the site root (favicons) |
| `public/admin/` | Sveltia CMS — `index.html` (loads the CMS) + `config.yml` (forms mirroring the collection schemas). Served at `/admin/`. Edits commit to the repo → host rebuilds |
| `astro.config.mjs` | Astro config — registers the Tailwind v4 Vite plugin (`@tailwindcss/vite`) |
| `tsconfig.json` | TypeScript config (extends `astro/tsconfigs/strict`) |
| `package.json` | Project manifest and npm scripts |
| `dist/` | Build output — gitignored, generated by `npm run build` |

## Task → File Routing

| Task | Files to read / edit |
|------|----------------------|
| Add a new page | Create `src/pages/<name>.astro`, wrap content in `BaseLayout` |
| Add a reusable component | Create `src/components/<name>.astro` |
| Change nav, site name, or brand | `src/site.ts` |
| Change colors, fonts, or base styles | `src/styles/global.css` (`@theme` tokens: `paper`, `mist`, `ink`, `muted`, `accent`) |
| Add/change a content collection or its schema | `src/content.config.ts` |
| Add a horse / tournament / photo entry | `src/content/horses\|tournaments\|photos/` + the image in `src/assets/` |
| Change Astro integrations or build config | `astro.config.mjs` |
| Add TypeScript paths or compiler options | `tsconfig.json` |
| Add a static asset (image, font, etc.) | `public/` |
| Change npm scripts or dependencies | `package.json` |

## Hard Constraints

- **File-based routing**: only files under `src/pages/` become routes. Do not place page files elsewhere.
- **TypeScript strict**: the project extends `astro/tsconfigs/strict`. Type errors will surface at build time.
- **Node ≥ 22.12.0**: enforced in `package.json` `engines` field.
- **No framework integrations**: plain `.astro` only — interactivity (mobile nav, gallery filters) is small vanilla `<script>` blocks, no React/Vue/Svelte. Adding one requires `astro add <integration>`. (`@astrojs/check` + `typescript` are devDependency tooling, not integrations.)
- **Styling is Tailwind v4 utilities + `@theme` tokens** in `src/styles/global.css` (imported once via `BaseLayout`). No `tailwind.config.js`; no `@tailwindcss/typography` (the horse-bio markdown is styled with plain utilities). Use the theme color names (`ink`, `mist`, `accent`, …), not hex literals.
- **All browser-facing images go through `<Image />`** (`astro:assets`) with meaningful `alt` — never a raw `<img>` or full-res original. Collection images come from `src/assets/` via the `image()` schema field; the hero is imported directly.
- **Content collections use the Content Layer API**: collections are defined in `src/content.config.ts` with `glob()` loaders and Zod schemas. Image fields use the `image()` schema helper (images live in `src/assets/`); cross-collection links use `reference('horses')`. Import Zod as `import { z } from 'astro/zod'` — importing `z` from `astro:content`/`astro:schema` is deprecated in Astro 6.
- **Horse age is computed, not stored**: schema stores `foaled` (birth year); derive age in the UI.

## Deployment & editing

- **Repo**: `IanStacked/samhorse` on GitHub (private), default branch `main`.
- **Hosting**: live at **https://samhorse.pages.dev/** via **Cloudflare Pages (static)** connected to the repo — build `npm run build`, output `dist`, auto-rebuilds on push. Must be a *static Pages* project: the **Workers** import flow injects `@astrojs/cloudflare`, which breaks `<Image />` (routes it to a runtime Images binding) and force-adds a KV SESSION binding that fails to deploy. This site is fully static and needs **no adapter** — verify build logs have no `[@astrojs/cloudflare]` lines.
- **CMS**: Sveltia CMS at `/admin` (`public/admin/`). `config.yml` collections **must stay in sync** with `src/content.config.ts` — if you add/rename a schema field, update both. Image fields use per-field `public_folder: ../../assets/<dir>` so saved paths are relative imports Astro can optimize.
- **CMS auth**: simplest is a GitHub Personal Access Token (no infra); one-click "Sign in with GitHub" needs a (free) Sveltia CMS Authenticator worker + GitHub OAuth app, set via `backend.base_url` in `config.yml`. Sveltia also runs locally with no auth at `localhost:4321/admin/index.html` (Chromium, File System Access API) for testing.

## Gotchas

- **Phantom `ImageNotFound` after deleting content entries**: the Content Layer store is persisted at `node_modules/.astro/data-store.json` (not under `.astro/`). When you delete a collection entry whose schema had an `image()` field, `astro sync` may keep the stale image import and the build fails with `ImageNotFound` for an asset you already removed. Fix: `rm -f node_modules/.astro/data-store.json` then rebuild.
- **Empty defined collections warn, not error**: calling `getCollection()` on a collection that exists in `content.config.ts` but has no entries (currently `tournaments`, `photos`) logs `"The collection … does not exist or is empty"` and returns `[]`. The build still succeeds; the warning clears once real entries are added.
